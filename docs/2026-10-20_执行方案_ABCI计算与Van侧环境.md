# 执行方案：ABCI 负责模型计算，OSWorld 环境放在 Van 侧（已定案）

> 2026-10-20 / ChuangMa 侧（opus5.5 执笔）。供 Van 确认。19:10 补记软件模拟（TCG）实测结果（§6）并按 §1 的规则定案：**分工**。
> 需要 Van 确认的事见 §7 第 2 条。

## 1. 结论

- OSWorld 的每个任务都要一台 Ubuntu 桌面虚拟机（VM）。ABCI 的批处理作业里**没有 Docker、没有 root、拿不到 KVM（CPU 硬件虚拟化）**。
  ABCI 是共享集群，这些系统层面的软件和设备权限由管理方统一配置，**我们不能额外安装或开启目前没有的东西**，也不打算去申请。
- 所以在 ABCI 上，VM 只能用 QEMU 纯软件模拟（TCG）跑：**能跑，但慢**。慢到影响实验效果就不用。
- 定案规则：
  - TCG 实测（作业 2726621）**全部通过 §4 的判据** → 全部在 ABCI 上跑（一个节点里 vLLM 和 VM 共置）。
  - **任何一条不过** → 分工（§5）：**ABCI 只做 GPU 计算**（4 个模型的 vLLM 推理服务 + 离线分析），**OSWorld 的 VM 和 harness 放在 Van 侧有 KVM 的机器上**。

## 3. 为什么软件模拟可能影响实验效果

- TCG 逐条翻译执行 VM 的指令，通常比 KVM 慢几倍到十几倍，桌面渲染和 Chrome 尤其慢。
- 官方 harness 每执行一个动作，`DesktopEnv` 等 2 s、EvoCUA 的 runner 再等 5 s，然后截图交给模型。
  环境慢 → 截图时界面还没变化 → 模型以为动作没生效 → **重新推理同一份计划、重复动作**。
- 本研究要测的恰恰是"跨步重复推理"（RRO、RRH、FAC@k）。环境慢造成的重复会被算成模型自身的冗余，**结论会被环境混淆**。
- 把等待时间调长能缓解一部分，但那是改官方设置；打字、滚动等所有操作都会变慢，补偿不完全。

## 4. TCG 判据（实测前写定）

在官方配置（4 vCPU / 4 GB）下**全部满足**才在 ABCI 上用 TCG（8 vCPU 的结果只作参考）：

1. LibreOffice Calc、Chrome 从启动命令到窗口出现 ≤ 7 s（即官方动作后等待的 2 s + 5 s 之内）；
2. 单个动作的开销（VM 内执行一次 `python3 -c "import pyautogui; ..."`，OSWorld 执行每个动作都是这样）≤ 2 s；
3. 截图请求 ≤ 3 s；
4. VM 内能上网；
5. 16 台并发都能起机，负载下截图仍 ≤ 3 s。

起机耗时只影响吞吐，不设门槛，只记录。

## 5. 分工方案（判据不过时采用）

### 5.1 结构

```
Van 侧机器（KVM + Docker）
  ├─ OSWorld VM × N（官方 docker provider）
  ├─ harness：EvoCUA 官方 runner；UI-Mate 的 OSWorld runner（我方写）
  ├─ 采集：trajectory.jsonl、截图、原始输出、report.html
  └─ 调模型：http://127.0.0.1:<Van侧端口>/v1
        ▲
        │  SSH 反向隧道：由 ABCI 主动连出 22 端口（ssh -N -R）
        │
ABCI 计算节点（PBS 作业，8×H200）
  └─ vLLM（OpenAI 兼容接口）：EvoCUA-8B / EvoCUA-32B / UI-Mate-9B / UI-Mate-27B
```

- ABCI 入站全拒，连接只能由 ABCI 发起：作业在计算节点上起好 vLLM 后，执行
  `ssh -N -R 127.0.0.1:<Van侧端口>:127.0.0.1:<vLLM端口> <Van侧机器>`；Van 侧 harness 设
  `OPENAI_BASE_URL=http://127.0.0.1:<Van侧端口>/v1`。隧道只绑 Van 侧本机回环地址，不对外暴露。
- VM 用 OSWorld 官方 docker provider（KVM 加速），与官方评测环境一致，不需要改 VM 相关代码。
- 我方代码（采集日志、UI-Mate 的 OSWorld runner、report.html、指标计算）都放本仓库，Van 侧拉下来运行。
- 原始轨迹落在 Van 侧。需要 GPU 的分析（例如用 LLM 从推理文本里抽取未来动作）经同一条隧道调用 ABCI 上的模型；
  轨迹需要拷回 ABCI 时由 ABCI 主动 `rsync` 拉取。

### 5.2 ABCI 侧（ChuangMa 负责）

- 一个 8 卡作业里同时起 4 个模型的 vLLM（例如两个大模型各 2 卡、两个小模型各 1–2 卡），8 卡用满。
- 两套 vLLM 环境：EvoCUA 按官方推荐的 vLLM 0.11；UI-Mate 用支持 qwen3_5 架构的新版。
  vLLM **不开 reasoning parser**：两个官方 harness 都只读 `message.content`，开了之后推理文本会进 `reasoning_content` 被丢掉。
- 预约队列会被白名单用户挤占（作业被 kill，exit 271）：作业写成可以直接重投，被挤后自动重排；隧道断开期间 Van 侧的请求会失败（见 §5.4）。

### 5.3 Van 侧需要提供

- 一台 Linux 机器：KVM + Docker（OSWorld docker provider 的要求）。每台 VM 约 4 vCPU / 4 GB 内存；16 台并发需要约 64 核、64 GB 以上内存；
  磁盘 ≥ 100 GB（`Ubuntu.qcow2` 24.5 GB + 每台 VM 的写时复制层）。
- 这台机器能从公网 SSH 登录（22 端口；不能直连的话经一台中转机）。给 ABCI 侧开一个只用于端口转发的账号（`AllowTcpForwarding yes`），
  接收我方公钥。
- 没有合适的机器时可以用云（OSWorld 支持 AWS，EvoCUA 官方评测命令就是 `--provider_name aws`），结构不变。

### 5.4 风险和处理

- **抢占造成的中断不能算模型失败**：UI-Mate 的 harness 请求失败 2 次后返回空串，被解析成 FAIL，episode 直接按失败结束；
  EvoCUA 每 30 s 重试一次、共 10 次。我方 runner 要识别"模型服务不可用"，把这条 episode 标为中断、之后整条重跑，不计入成功率和各项指标。
- **延迟口径**：日本—湾区往返约 0.1–0.2 s，每次请求带最多 5–6 张截图（几 MB），会多出 1 到数秒。
  推理代价以 ABCI 侧 vLLM 记录的生成时间和 token 数为准；harness 侧的端到端耗时单独记录，不混用。
- UI-Mate 默认请求超时 130 s。长推理（`max_tokens` 16384）在服务繁忙时可能超时，需要在 runner 里调大超时（只改超时，不改解码参数）。
- 吞吐（估算）：pilot 4 模型 × 30 任务 = 120 条 episode；16 台 VM 并发、每条按 20 分钟算，约 2.5 小时。

## 6. TCG 实测结果（作业 2726621，2026-10-20 18:54–19:04，hnode571，exit 0）

| 项 | 4 vCPU（官方配置） | 8 vCPU | 对应判据 |
|---|---|---|---|
| 起机（VM 内 server 就绪） | 70 s | 92 s | 不设门槛 |
| 截图请求 | 0.34–0.85 s | 1.06–3.14 s | ③ ≤ 3 s：4 vCPU 通过 |
| 动作请求（VM 内 `python3 -c "import pyautogui; pyautogui.moveTo(200, 200)"`） | 1.13–1.22 s | 1.61–1.82 s | ② ≤ 2 s：请求耗时通过，但**动作没有反映到画面上**（见下） |
| LibreOffice Calc / Chrome 打开 | 没测出 | 没测出 | ① ≤ 7 s：**不通过** |
| VM 内上网 | 没测出 | 没测出 | ④ 能上网：**未证实** |
| 16 台并发 | 16/16 在 119 s 内就绪，负载下截图约 1 s | — | ⑤ 通过 |

- **桌面没有画出来**：起机 60 s 后的截图，和又过约 1 分钟（执行完移动鼠标、打开应用之后）的截图，都是全黑、只有一个鼠标指针，md5 完全相同。
  X 服务在跑，但 GNOME 桌面一直没出现，移动鼠标也没有体现在画面上。
- 打开应用、VM 内上网这几条命令经 `/execute` 返回的输出为空，原因没有查清；同一接口执行的简单命令（`nproc`、`free`、`ip addr`）能正常返回
  （VM 内 4 / 8 核、3.9 GB 内存、IP 20.20.20.21 都对）。
- **定案（按 §1 的规则）**：判据 ①、④ 不通过 → **采用 §5 的分工**。软件模拟不再在 ABCI 上继续排查：
  即使桌面最终能调出来，慢速环境会混淆重复推理指标的风险（§3）依然存在。
