## 3. 实验需求摘要（MOTIVATION.md）

- **问题**：强 GUI agent 第 t 步的推理里，是不是已经写出了后面好几步的动作，而后面的步骤又把同一份计划重新推一遍？
  本阶段**只做动机验证**，不训练 JEV / executor / 任何替代策略。
- **模型**：EvoCUA-8B、EvoCUA-32B、UI-Mate-9B、UI-Mate-27B（两族 × 两尺寸，可做跨族和族内缩放对比）。
  只有 harness 暴露推理时真实产生的推理文本的模型才能进主分析，不许事后重建 CoT。
- **基准**：OSWorld-Verified；任务 ID、环境初始化、步数上限、评测器版本、官方 prompt、动作解析器、解码参数尽量固定，**只允许加日志**。
- **Pilot**：4 个模型跑同一批 30 个任务；在搭自动分析流水线之前，先人工看 100–200 个推理步，回答：一步推理里是否明显包含多个可执行的未来动作？
  后面的推理是否明显重复已说过的动作意图？推理结构能否可靠解析？现象是否足够常见？几乎全是单步规划就在扩大规模前停。
- **原始轨迹**：每个任务一个自包含文件夹 `trajectories/<model>/<task_id>/`：`meta.json`、`trajectory.jsonl`（每步一行：截图路径、原始输出、
  推理、原始动作、执行动作、token、延迟、成功与否）、`report.html`、`step_XXX/{before.png, after.png, raw_output.txt, reasoning.txt, action.json}`。
  原始输出和原始动作永远保留，派生标注另存。
- **report.html**：按步展示指令、截图（前）、完整原始输出、抽出的推理、执行动作、截图（后）、token/延迟；`Reason_t` 与 `Reason_{t+1}` 并排或相邻，
  一眼能看出重复。HTML 不能替代原始日志。
- **动作语义化**：统一到 `CLICK(target) / TYPE(text,target) / SCROLL / PRESS / HOTKEY / DRAG / WAIT / DONE / OTHER`；坐标点击要用动作前截图识别语义目标。
- **从推理中抽未来动作**：解析器只能看任务指令和当前推理，**不能看未来动作、未来截图、最终结果**；宁可漏报不可编造。
- **指标**：多动作规划率 MAPR（含 ≥2 个可执行动作意图的推理步比例）；未来动作覆盖率 FAC@1…5（后 k 个实际动作有多少已在 `Reason_t` 中写出）；
  推理复用长度 RRH（实际动作中已被 `Reason_t` 覆盖的最长连续前缀；报均值、中位数、CDF、P(RRH≥2/3/5)）；
  重复推理重叠 RRO（后一步推理的动作意图有多少已出现在前面）；推理代价（token、延迟、调用次数，称为"潜在可复用代价"而非"节省"）。
- **对照**：全部 / 成功 / 失败轨迹；短 / 中 / 长任务；8B→32B、9B→27B。文本相似度只能做辅助诊断，主分析必须基于语义动作。
- **人工验证**：随机抽 200–300 个推理步人工标注，报解析/对齐的 P/R/F1。
- **继续/止损**：两族都普遍出现"一次推理规定多步、RRH 常 > 1、FAC@2/3 显著、后面重复重算"才进入方法阶段；否则停或改题。
- `scripts/README.md` 列的 7 个脚本：`collect_rollouts.py`、`build_trajectory_report.py`、`semanticize_actions.py`、
  `extract_future_actions.py`、`align_actions.py`、`compute_metrics.py`、`sample_human_validation.py`。

### 5.2 推理文本是否可得（资格要求）

- **EvoCUA**：chat template 的生成前缀是 `<|im_start|>assistant\n<think>\n`，模型先输出思考再输出答案。官方 S2 格式要求答案部分只有
  `Action: <一句话>` + 一个 `<tool_call>`；规划内容在 `<think>` 段里。
- **UI-Mate**：prompt 明确要求 `<think>…</think>`（"step by step progress assessment and next action analysis"）→ `<action>` → `<tool_call>`；
  默认把历史步骤的 thinking 也放回上下文（`include_thinking_in_history=True`）。
- **关键注意**：两个官方 harness 都只读 `message.content`。vLLM 若开 `--reasoning-parser`，思考会进 `reasoning_content` 被丢掉。
  采集时 vLLM 不开 reasoning parser，或者采集器同时保存 `content` 和 `reasoning_content`。
- 官方解码设置：EvoCUA `temperature 0.01, max_steps 50, max_history_turns 4, coordinate_type relative, resize_factor 32, prompt_style S2`
  （推荐 vLLM 0.11.0 / transformers 4.57.3）；UI-Mate `max_tokens 16384, temperature 1.0, top_p 0.95, enable_thinking True`
  （需要支持 qwen3_5 的新版 vLLM / transformers 5.x）。两族需要两套 vLLM 环境。
- **harness 差距**：EvoCUA 有官方 OSWorld runner（`run_multienv_evocua.py`，OSWorld 主仓也收录了 `mm_agents/evocua`）；
  **UI-Mate 只给了 agent 类（`agents/ui_mate_agent.py`），没有 OSWorld runner，需要我们按 OSWorld 的 `lib_run_single` 自己写**。

### 5.3 OSWorld 的 VM 在 ABCI 上怎么跑

- OSWorld 的 docker provider 用镜像 `happysixd/osworld-docker`（qemus/qemu-docker 改版）：`-v Ubuntu.qcow2:/System.qcow2:ro`，
  容器把 VM 端口 5000（控制 server）/ 9222（Chrome CDP）/ 8006（VNC 网页）/ 8080（VLC）映射到宿主机；`DesktopEnv` 认的 vm_ip 串是
  `host:server:chrome:vnc:vlc`（`rsplit(':', 4)`）。
- ABCI 没有 Docker，有 Singularity 4.4。镜像 `entry.sh` 需要 root + NET_ADMIN，不能直接跑。
- 做法：绕开 `entry.sh`，用镜像里的 QEMU 9.1 + KVM 直接起 VM，参数照抄镜像默认值：
  `q35 + KVM, -cpu host, 4 vCPU, 4G, UEFI(edk2-x86_64-code.fd), -hda <qcow2 overlay → Ubuntu.qcow2>, -vga virtio, virtio-net-pci, 客户机 IP 20.20.20.21`。
  只有网络不同：镜像用 tap 网桥 + NAT，我们用 slirp 用户态网络 + 端口转发（每台 VM 一组 127.0.0.1 端口：slot s → 20000+10s 起 4 个）。
  每次 start 新建 overlay，等价于 OSWorld 的 revert_to_snapshot。
- VM 镜像：`xlangai/ubuntu_osworld` 的 `Ubuntu.qcow2.zip`（12,273,896,463 字节）。
- 登录节点 `/dev/kvm` 是 `crw-rw-rw-`，容器内可用；计算节点待探测。
